# OpsPilot 容器化部署

> 状态：生产化基础链路  
> 更新时间：2026-08-25  
> 范围：PostgreSQL、数据库迁移、控制面、前端、Runner

## 1. 部署结构

根目录 `docker-compose.yml` 提供以下服务：

| 服务 | 作用 | 启动条件 |
|---|---|---|
| `postgres` | PostgreSQL 17 持久化存储 | 默认启动 |
| `migrate` | 执行 `alembic upgrade head` 的一次性 Job | PostgreSQL 健康后运行 |
| `backend` | FastAPI 控制面 | Migration Job 成功后启动 |
| `frontend` | 非 Root Nginx 静态站点和 `/api/` 同源代理 | 后端 Ready 后启动 |
| `runner` | 隔离的只读观测与受控 Action 执行面 | 使用 `runner` Profile 显式启动 |

后端和 Runner 镜像使用 UID/GID `10001`，前端使用
`nginx-unprivileged` 的非 Root 用户。API、Migration 和 Runner 容器启用只读根文件系统、
`no-new-privileges` 并移除 Linux Capabilities。

## 2. 推荐：跨平台一键启动

本地体验只要求安装 Python 3.12/3.13、Docker Engine（或 Docker Desktop）和
Docker Compose v2。根目录启动器只使用 Python 标准库，因此 Windows、Linux 和 macOS 使用
同一入口：

```bash
# 首次运行会构建镜像、执行迁移、启动服务并等待 Ready
python main.py

# Linux 发行版通常使用这个命令名
python3 main.py
```

启动成功后访问 `http://127.0.0.1:8080`。启动器会生成缺失的本地 Secret，但绝不会覆盖已有
Secret；第一次进入控制台时按提示创建初始 Admin。常用运维命令如下：

```bash
python main.py doctor          # 校验 Docker 和标准 Compose
python main.py status          # 查看服务状态
python main.py logs --follow   # 跟踪日志
python main.py stop            # 停止服务，保留数据库卷
python main.py start --lab     # 同时启动 Runner 和 Fault Lab
python main.py doctor --lab    # 校验 Fault Lab Compose 覆盖
```

只有明确希望清空本地数据库和 Lab 数据时才使用
`python main.py stop --lab --remove-volumes`。该命令会永久删除 Compose 数据卷。

Linux 完全支持该入口。若出现 Docker Socket 权限错误，优先使用 Rootless Docker；也可把当前用户
加入宿主机的 `docker` 组后重新登录（注意该组近似拥有宿主机 Root 权限）。启用 Runner 时还应将
`stat -c '%g' /var/run/docker.sock` 的结果写入 `.env` 中的 `OPSPILOT_DOCKER_GID`。生产部署仍应
使用外部 Secret Manager、TLS 入口和正式编排平台，`main.py` 定位是本地开发、演示与单机验收。

前端端口默认只监听 `127.0.0.1`。在远程 Linux 服务器验收时，推荐从本机建立 SSH 隧道：

```bash
ssh -L 8080:127.0.0.1:8080 user@server
```

然后仍从本机访问 `http://127.0.0.1:8080`。不要为了临时验收直接把端口暴露到公网；正式公开
访问应由 HTTPS 反向代理承接，并同步配置可信代理、Secure Cookie 和允许的 Origin。

## 3. 准备 Secret

复制示例文件：

```powershell
Copy-Item .env.compose.example .env
```

修改 `.env` 中的四个 Secret，每个值应独立随机生成：

```env
OPSPILOT_POSTGRES_PASSWORD=...
OPSPILOT_ALERTMANAGER_WEBHOOK_TOKEN=...
OPSPILOT_RUNNER_BOOTSTRAP_TOKEN=...
OPSPILOT_CONTROL_PLANE_BOOTSTRAP_TOKEN=...
```

`.env` 已被 Git 忽略。Compose 仅使用这些值创建 Secret 文件；应用容器通过 `/run/secrets/*`
读取，不把明文 Token 或数据库密码写入容器环境变量。不要把 `.env` 提交、打包进镜像或复制
给浏览器。

首次启动或 Secret 轮换后生成 Compose 文件型 Secret：

```powershell
.\scripts\prepare-compose-secrets.ps1
# 轮换已有文件时显式覆盖
.\scripts\prepare-compose-secrets.ps1 -Force
# 没有旧接入 Token 时显式生成缺失的非数据库 Secret
.\scripts\prepare-compose-secrets.ps1 -GenerateMissing
```

Linux/macOS 使用跨平台启动器生成并校验默认文件型 Secret：

```bash
python3 main.py doctor
```

`.secrets/` 已被 Git 忽略。文件型 Secret 允许 API、Migration 和 Runner 继续使用只读根文件系统；当前 Compose 不支持把环境变量型 Secret 挂载到 `read_only` 服务。也可以通过 `OPSPILOT_COMPOSE_*_FILE` 变量指向仓库外由 Secret Manager 投放的文件。

Linux 上 Compose 会把本地文件型 Secret 实现为只读 bind mount，并保留宿主文件的所有权。
因此默认 `.secrets/` 目录必须保持 `0700`，其中 Secret 文件使用 `0644` 供容器内非 root UID
读取；其他宿主用户无法穿越 owner-only 目录。若通过 `OPSPILOT_COMPOSE_*_FILE` 使用外部
Secret Manager 文件，也必须确保目标容器 UID 对文件具有只读权限。

## 4. 手动构建并启动控制面

```powershell
docker compose config --quiet
docker compose build backend frontend
docker compose up -d postgres migrate backend frontend
docker compose ps
```

Migration Job 必须以退出码 `0` 完成，后端才会启动。检查日志：

```powershell
docker compose logs migrate
docker compose logs backend
```

默认访问地址：

- 控制台：`http://localhost:8080`；
- 后端健康：`http://127.0.0.1:8000/api/v1/health`；
- 后端就绪：`http://127.0.0.1:8000/api/v1/ready`。

Compose 使用 `production` 环境并默认关闭 OpenAPI、Swagger 和 ReDoc。前端请求同源
`/api/v1`，Nginx 对 SSE 关闭代理缓冲并延长读取超时。

该单机模板为本地 `http://localhost` 显式关闭后端 HTTPS 强制，并允许 Runner 在私有 Compose
网络使用 HTTP。真实生产入口必须删除这两个例外，配置 TLS 终止，将
`OPSPILOT_TRUST_FORWARDED_PROTO` 设为 `true`，并确保代理覆盖客户端伪造的转发 Header。跨主机
Runner 必须使用 `https://.../runner/v1`。

## 5. 启动 Runner Profile

先使用控制面创建 Environment，再把 UUID 写入根目录 `.env`：

```env
OPSPILOT_RUNNER_ENVIRONMENT_ID=环境UUID
OPSPILOT_RUNNER_NAME=docker-runner
```

Linux 还需填写 Docker Socket 的组 ID：

```bash
stat -c '%g' /var/run/docker.sock
```

将输出写入 `OPSPILOT_DOCKER_GID`，然后启动：

```powershell
docker compose --profile runner build runner
docker compose --profile runner up -d runner
docker compose --profile runner ps
```

Runner 凭据保存在命名卷 `opspilot-runner-data`，重建容器不会丢失。Runner 容器只挂载
Docker Socket，不包含 Docker Daemon。Windows Docker Desktop 使用 Linux Container 模式时由
Docker Desktop 转发该 Socket；如果宿主机策略禁止挂载 Socket，应把 Runner 部署到独立主机，
不要提高控制面容器权限。

Compose 内 Runner 连接 `http://backend:8000/runner/v1`，不会经过前端 Nginx 的用户面代理。
如果 Runner 部署在外部主机，入口代理必须单独转发 `/runner/v1`，且不能把 Runner Token
交给浏览器。外部 Agent Runtime 如需使用 HTTP 内部接口，应只在受信网络转发
`/internal/v1`，并使用独立的 `service/runtime` Principal；内置 Runtime 直接调用后端 Service。

## 6. 健康检查与升级

| 服务 | 健康依据 |
|---|---|
| PostgreSQL | `pg_isready` |
| Backend | `/api/v1/ready`，包含数据库和已启用 Worker 检查 |
| Frontend | Nginx `/healthz` |
| Runner | 本地凭据存在且控制面 `/health` 可达 |

升级前先备份 PostgreSQL。更新代码后执行：

```powershell
docker compose build backend frontend
docker compose up -d postgres migrate backend frontend
docker compose --profile runner build runner
docker compose --profile runner up -d runner
```

数据库结构只允许通过 Migration Job 前滚。不要在应用启动命令中并发执行 Alembic，也不要在
没有备份和迁移回滚评估时直接执行 `alembic downgrade`。

## 7. 当前边界

- Compose 是单机生产化基础模板，不替代 Kubernetes、外部 Secret Manager 或托管数据库；
- 前端、后端和 PostgreSQL 默认仅监听宿主机回环地址；TLS 应由负载均衡器或反向代理终止，
  公网部署不得直接暴露 8080/8000/5432；
- Runner Token 已支持在线轮换、有效期和宽限恢复；
- Runner 与控制面之间的 mTLS 尚未实现；当前依赖 HTTPS 和可轮换 Token，跨主机部署必须限制
  Runner API 的网络入口；
- Agent Runtime 默认关闭，启用时还需通过 Secret 管理器注入模型 API Key；
- Worker 心跳、最近成功时间、错误计数和 `/ready` 联动已实现；多实例独立 Worker 拆分仍是
  后续部署演进项；
- Outbox Publisher、Webhook 重试、Dead Letter 和保留清理已实现；外部 Webhook 接收方必须按
  `eventId` 幂等去重。

再次强调：根目录 Compose 是本地单机 HTTP 模板。它显式关闭 HTTPS 强制，并允许 Runner 在
Compose 私有网络使用 HTTP。真实生产部署必须使用 HTTPS 入口、`Secure` Cookie、可信转发头
配置和独立 Secret 管理器，不能把模板中的 HTTP 例外原样用于公网。
